# 05.4 Review mutations

## Goal
`writeReview`, `updateReview` and `deleteReview`, where users can only edit their own Reviews.

## Notes
- `writeReview(bookId, rating, text)` requires a Viewer; it fails if the Viewer already has a Review for the Book (one per User per Book).
- `updateReview(id, ...)` and `deleteReview(id)` load the Review and check it's the Viewer's, otherwise `FORBIDDEN`.
- Rating outside 1–5 or not a whole number → `BAD_USER_INPUT`. Should the schema enforce this as well (a custom scalar? documentation only?), or only the resolver?
- After a write, `Book.averageRating` in the response must be current. Check what the router fetches if the client selects `book { averageRating }` on the result.

## Acceptance criteria
- [ ] Logged in as `sam`, `updateReview` on `andreas`'s Review → `FORBIDDEN`. On `sam`'s own Review it succeeds.
- [ ] A second `writeReview` for the same Book → error, according to your convention.
- [ ] Tests cover all of the above, plus `averageRating` changing after a write and after a delete.

## Concepts practised
Resource ownership checks · input validation · how mutation results cross subgraphs
