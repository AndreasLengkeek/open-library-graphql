# 06.1 Docker Compose

## Goal
`docker compose up` runs the whole supergraph: three subgraphs and the router, seeded and ready.

## Notes
- One multi-stage Dockerfile per service (build with pnpm, run on `node:26-slim`). `better-sqlite3` ships Linux prebuilt binaries for glibc; if you use Alpine (musl), check that it still installs.
- SQLite files live on named volumes. A one-off `seed` service (or a profile) runs `pnpm seed`.
- Router: the official `ghcr.io/apollographql/router` image. **Default mode:** run it from a locally composed `supergraph.graphql` (`--supergraph`), with `router.yaml` mounted. Change the routing URLs to the Compose service names, using a separate `supergraph.docker.yaml` or env overrides.
- Healthchecks on each subgraph; the router `depends_on` them being healthy.
- Secrets (`JWT_SECRET`, `OPEN_LIBRARY_USER_AGENT`) come from `.env`. Commit a `.env.example`.
- Optional: `@libsql/client` would let you point a subgraph at a remote database later (Turso or a `sqld` container) without code changes. Only consider it if you plan to deploy the subgraphs somewhere without a persistent disk.

## Acceptance criteria
- [ ] From a clean clone: `cp .env.example .env && docker compose up --build`, then `MyShelves` works at `http://localhost:4000` after logging in as `andreas`.
- [ ] `docker compose down && docker compose up` keeps the data. `docker compose down -v` resets it.

## Concepts practised
Containerising Node subgraphs · running the router from a static supergraph · service discovery by name
